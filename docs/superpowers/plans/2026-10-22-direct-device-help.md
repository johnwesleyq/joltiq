# Direct Device Help Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a user ask JoltIQ for help directly from the installed Windows companion while preserving the internal ticket, consent, verification, and escalation model.

**Architecture:** Add device-authenticated support-request endpoints that reuse the existing ticket and agent-run services, then add a WinForms conversation window driven by `AgentClient`. Device authentication supplies all identity and device linkage; a client request ID provides idempotency. The direct channel never carries action or consent fields and cannot bypass the existing computer-use session gates.

**Tech Stack:** FastAPI, SQLAlchemy/PostgreSQL, Python/pytest, .NET 8 C#, Windows Forms, existing ECDSA device protocol.

**Spec:** `docs/superpowers/specs/2026-10-22-direct-device-help-design.md`

## Global Constraints

- All device requests use the existing signed request protocol and tenant scoping.
- Direct help creates a durable internal ticket with source `device_chat` and the authenticated device ID.
- The server derives all identity fields; client-supplied identity or consent fields are rejected by schema validation.
- Conversation start grants no screen or input permission.
- Production never falls back to an external computer-use model.
- Existing unrelated untracked files remain untouched.

## Review Focus

- Duplicate or retried first messages must create exactly one ticket and run.
- A device must not read or write another device's conversation, even in the same tenant.
- Revoked, unowned, or stale-owner devices must fail closed without leaking ticket existence.
- Tray network failure must not show a message as submitted or discard the user's draft.
- Direct help must not create a session, consent record, approval, or device command before the existing workflow requests one.

## Self-review

- Spec coverage: direct start, continuation, status, identity binding, idempotency, consent separation, offline behavior, revocation, and macOS reuse are assigned to Tasks 1–5.
- Type consistency: the API `run_id` is a string UUID throughout; only creation accepts a UUID `client_request_id`; continuation and reads derive the ticket through the authenticated device/run relationship.
- Review-focus coverage: duplicate, cross-device, revoked/ownerless, offline draft retention, and premature-control cases each have an explicit owning test.
- Proportion: implementation details reuse existing services; no new general chat or action engine is introduced.
